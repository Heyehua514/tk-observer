# 生产部署与恢复

## 当前已落地

- 前端安全门禁：`node scripts/security/production-gate.mjs`
- 桌面端 updater 配置入口：`apps/desktop/src-tauri/tauri.conf.json`
- 桌面端更新插件默认编译进客户端；没有清单地址或签名公钥时只显示“更新服务尚未配置”，不会发起下载。
- CSV 导入提交前会校验必需列、空文件和重复的“标题 + 发布日期”主键。

## 每次发布前

1. 执行 `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build` 和 `git diff --check`。
2. 执行 `node scripts/security/production-gate.mjs`，发现前端 `service_role` 立即停止发布。
3. 更新地址和公钥已经固定在 Tauri 配置与发布工作流中；发布环境只需要注入签名私钥和私钥密码，再执行 `pnpm desktop:build`。
4. 将 DMG/NSIS 安装包、macOS `.app.tar.gz`、签名文件和 updater manifest 发布到同一 HTTPS 地址。

## 自动发布

推送形如 `v0.1.1` 的 tag，或从 GitHub 手动指定同名 tag，会触发 `.github/workflows/desktop-release.yml`，在 macOS 和 Windows runner 构建并自动发布正式 Release。手动发布时，workflow 会先把该 tag 创建到当前提交；如果该 tag 已经指向其他提交会停止，绝不覆盖历史版本。两个平台会按顺序上传，避免同时写入同一 Release 造成同名资产冲突。macOS 会同时产出 DMG 安装包和供 updater 使用的 `.app.tar.gz` 签名归档。发布前 workflow 会执行 `pnpm desktop:release:check`：`apps/desktop/package.json`、`apps/desktop/src-tauri/Cargo.toml`、`apps/desktop/src-tauri/tauri.conf.json` 必须是同一个版本；GitHub 的发布 tag 也必须等于 `v<客户端版本>`。任一项不符合会在构建前失败，且不会输出密钥。

GitHub 配置：

- Repository Secrets：`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
- `GITHUB_TOKEN` 使用 GitHub 自动提供的 token，不要另建明文 token

每次发布完成后，管理员仍需核对安装包、签名文件和 manifest。发布地址必须是 HTTPS，并且 manifest 中的平台包 URL 要能被客户端访问。客户端随后可在“设置 → 检查更新”获取已发布版本。

## 当前仍需线上配置

- Tauri updater 的签名私钥只能放在 CI Secrets，不能进入仓库。
- Supabase migration 需要由管理员在目标项目执行并记录版本。
- 微信视频号采集器需要授权的 Android/ADB 设备；当前 GitHub 项目不是微信官方 API，不能把未验证的采集结果当作生产数据。

## 备份与恢复

发布数据库 migration 前，先导出 Supabase 数据库和 Storage 文件清单，并保存到公司受控备份位置。恢复时先在临时项目验证 migration 和 RLS，再切换生产连接；不要直接修改已发布 migration。

CSV 导入失败时，当前客户端会在数据库 mutation 前阻止格式错误和重复主键。若需要“整批事务回滚”，应在 Supabase 增加 staging/import RPC 后再启用，不能用逐行客户端写入冒充事务。

## 需要重启

- Web：部署新构建后刷新浏览器即可。
- 桌面端：安装新构建包；启用 updater feature 后，需重新打包客户端。
- Supabase：应用 migration 后由平台自动加载；本地开发需重启对应服务。
