## AI 上下文安全与个人记忆排序

- 任务分析请求进入 WorkBuddy 前新增确定性脱敏：`password`、`passwd`、`token`、`secret`、`api key` 与 `Bearer` 凭据会替换为「[已脱敏]」。该处理只作用于发送给本机网关的任务备注，不修改原始任务数据。
- 个人记忆在发送前先按当前工作台或任务类型筛选，再按「当前工作台优先 → 置信度 → 最近使用时间」排序，最多发送 8 条。数据仍由既有 owner-scoped RLS 查询提供，不新增表、不扩大读取范围。
- 自我攻击覆盖：嵌入备注的敏感文本、15 条任务的 12 条上限、跨工作台高置信度记忆、同工作台置信度/最近使用排序、10 条可用记忆的 8 条上限。
- 并行前端切片 `299bffe feat(editing): show competitor traffic signals`：对标账号和视频显示紧凑粉丝/播放量、互动率、相对均播信号；热点模块继续复用现有来源、热度、更新时间、人工录入与转选题流程，不伪造平台实时数据。
- 验证：`pnpm typecheck`、`pnpm lint`、本轮文件 Prettier check、`pnpm test`（142 文件 / 322 测试）、`pnpm build`、`git diff --check` 通过。全库 Prettier 仍有 15 个既有历史文件告警，本轮未批量改写。

### 反思

- 敏感信息识别属于确定性问题，用本地正则和测试比请求 LLM 更快、更便宜、可回归；后续只在新增凭据格式时补充规则和攻击用例。
- 排序在本地现有 RLS 结果上完成，避免为短提示词新增数据库字段、查询和 migration。下一阶段若要记录「采用/拒绝」效果，应单独追加 schema 并先定义保留周期，不能混入本次安全修复。
- 浏览器组件测试的 module mock 必须补齐被间接依赖的导出；本次全量测试及时发现该错误，已在对标切片测试中修复。

## AI 记忆数据库攻击回归与 Supabase 本地门禁恢复

- 根因复现：本地 Supabase 的 migration 历史已标记 `20260821000300_ai_memory.sql`，但实际 schema 缺少 `ai_memory`；全量 pgTAP 因此失败。重建本地测试库后，迁移序列完整执行，未写入远程 Supabase。
- 修复测试契约：`ai_memory.eval.test.sql` 改为直接查询 PostgreSQL 约束目录，精确校验两个约束名；原 `has_check` 调用使用了本机 pgTAP 不支持的四参数形式。`ai_memory.test.sql` 同步修正断言总数和索引断言参数。
- 自我攻击：新增双账号 RLS 回归。账号 B 无法读取账号 A 的个人记忆、无法改变 A 的记忆值，也不能伪造 A 的 `owner_id` 建立记忆；测试事务自动回滚。
- 发现并修复 Realtime 审计漂移：`ai_memory` 已由 migration 发布到 `supabase_realtime`，但白名单测试未登记，现已显式纳入，防止后续新增实时表绕过清单审计。
- 验证：AI 记忆专项 13 项通过；Realtime + AI 专项 16 项通过；`pnpm supabase:test` 37 文件 / 554 条测试通过；`pnpm supabase:schema:test` 2/2、typecheck、lint、前端 142 文件 / 322 条测试、build、diff check 通过。

### 反思

- 数据库门禁失败先单跑最小 SQL 文件，可以把 migration 状态、pgTAP 兼容性和测试计数问题拆开定位，避免在 554 条测试输出中浪费排查时间。
- 发布 Realtime 表属于可审计安全边界，migration 与允许列表必须同步。后续每个新增 Realtime migration 都应在同一提交扩展审计测试。
- 本地测试环境因镜像拉取阻塞时，先检查已有兼容镜像和容器状态，避免并行启动多个 Supabase CLI 进程重复拉取镜像和争用 Docker 资源。
